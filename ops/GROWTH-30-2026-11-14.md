would grow the site significantly, then said to do everything that can be

## Blocked here, with the reason

- **Fitbit Web API graveyard entry.** It is `dying` with end 2026-11-02, so
  GRAVEYARD-DYING fails every build from **2026-11-16**. Google's pages
  (developers.google.com/health/about and /health/migration, both last
  updated 2026-10-30, read 2026-11-14) still say the endpoints "will be
  turned off"; dev.fitbit.com still says October 30. The only past-tense
  statement is the body of the endpoint's own 410: a GET of
  https://api.fitbit.com/oauth2/token answered "The legacy Fitbit Web API and
  OAuth 2.0 endpoints were decommissioned on October 30, 2026." (source-snapshot
  run 43653468316). scripts/check-source-quotes.mjs treats every non-2xx answer
  as a failure, so citing it would turn source-quotes red. Moving the entry to
  dead on that body, or teaching the checker an expected status, is a
  sourcing-policy decision left for the owner.
- **New pages** (MoveNet vs YOLO Pose, RTMPose vs MediaPipe, a published
  pricing history): the governor is closed with 0 new pages allowed this
  week. Queue them for when `ops/INDEX.md` reopens.
- **Snippet rewrites** for /blog/health-connect-sdk-release-history,
  /health-connect/permissions and /health-connect-api/read-health-data-history:
  their query rows are anonymized, so there is nothing to write toward; left
  to the daily loop.
- **Weak clusters.** phone-sensors (0 impressions, 10 pages) reaches 60 days
  on 2026-12-02. Decide then whether to fold it into /health-connect and
  /healthkit or noindex it, using the same zero-impression test the
  index-demand rule applies to generated pages.
