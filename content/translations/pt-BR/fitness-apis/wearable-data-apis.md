Se você precisa de uma API de wearable de fitness, a escolha depende mais de uma coisa do que de dados ou de preço: da facilidade de conseguir aprovação para ler dados de outras pessoas. Todas as cinco principais opções aqui — Fitbit (agora Google), Garmin, Oura, WHOOP e Polar — usam `OAuth 2.0` com consentimento por usuário. A documentação do Oura diz que a API dele é gratuita para apps pessoais e comerciais, e os termos do WHOOP e da Polar dizem que as deles hoje são gratuitas; a Garmin não publica preço para o Starter Access, e as páginas da Health API do Google não listam taxa de API, mas exigem uma avaliação de segurança que tem custo próprio (sempre confira os termos comerciais atuais). O que de fato as separa é o portão de aprovação, a profundidade dos dados e, no caso da Fitbit, a passagem para a Google Health API, que substituiu a Fitbit Web API legada.

Procura o melhor agregador de dados de saúde de wearables, uma API que cubra muitos wearables e sensores? É outro produto, e a [comparação de APIs agregadoras de dados de saúde de wearables](/fitness-apis/health-data-aggregator-apis) trata dele: Terra, Junction, Rook, Spike, Sahha, Thryve, Validic e Open Wearables. Só precisa dos seus próprios dados do Garmin Connect? A [Personal API oficial da Garmin para uso pessoal](/fix/garmin-api-personal-use) não exige aprovação no Developer Program.

Veio pelos passos de cadastro e OAuth de um fornecedor específico? Cada um tem o seu guia: os guias de integração da [API da Garmin](/integrate/garmin-api), da [API da Fitbit](/integrate/fitbit-api), da [API do Oura](/integrate/oura-api), da [API do WHOOP](/integrate/whoop-api) e da [API da Polar](/integrate/polar-api).

## O que observar em uma API de wearable

Quatro critérios decidem esta categoria. Pese-os nesta ordem:

- **Atrito de acesso e de aprovação.** Nenhuma delas é um feed de dados em massa. Cada uma devolve dados só de usuários individuais que autorizam o seu app, e a maioria condiciona o acesso de produção a um pedido ou a uma etapa de revisão. Essa é, na prática, a maior diferença entre elas — uma API autosserviço que você lança nesta semana versus uma que exige uma aprovação de parceiro que você pode não conseguir.
- **Adequação do modelo de dados.** Detalhe de GPS e multiesporte, métricas de bem-estar do dia todo, pontuações de sono e recuperação, HRV, `SpO2` — cada ecossistema de dispositivos pende para um ponto forte diferente. Combine a API com a métrica de que o seu produto realmente precisa.
- **Modelo de preço.** Nenhuma das cinco publica taxa por chamada em novembro de 2026. O Oura diz que a API dele é gratuita, o WHOOP e a Polar dizem que as deles hoje são gratuitas, a Garmin não publica preço para o Starter Access e ajusta os termos do Enterprise, e o Google estima entre US$ 500 e US$ 4.500 as taxas da avaliação de segurança feita por terceiros que os escopos restritos dele exigem. O resto do custo é (a) passar pela etapa de aprovação e (b) os seus usuários terem o hardware — e, no caso do WHOOP, uma assinatura do WHOOP. Sempre confira os termos comerciais atuais para uso em escala.
- **Migração e estabilidade.** APIs mudam. O [guia de migração do Fit](https://developer.android.com/health-and-fitness/health-connect/migration/fit) do Google, atualizado em 10 de setembro de 2026, lista a Google Health API como o caminho recomendado para integrações com a Fitbit Web API, então tudo o que você construir para a Fitbit deve mirar nela.

Uma observação sobre o atrito de aprovação em toda esta página: é um requisito factual de acesso, não uma crítica a nenhum produto. Um portão de revisão mais rígido muitas vezes reflete um tratamento mais rigoroso dos dados dos usuários. Para pôr duas delas lado a lado nesse portão, na cobrança do desenvolvedor e no que cada usuário precisa ter, use [a ferramenta de comparação de APIs](/compare-apis).

## Fitbit (Google Health API)

A Fitbit é melhor para alcance amplo no grande público, com dados ricos de sono, frequência cardíaca e intradiários, e esses dados agora chegam pela Google Health API do Google, que o Google descreve como a Fitbit Web API "improved and modernized" [aprimorada e modernizada] e renomeada. O Google diz que todos os dispositivos Fitbit e os Google Pixel Watch, atuais e anteriores, coletam dados que a API devolve. O índice de tipos de dados dela inclui passos, frequência cardíaca (armazenada com resolução de 1 segundo), variabilidade da frequência cardíaca, saturação de oxigênio, sono, exercício e VO2 máx., cada um sob um escopo de leitura como o escopo de sono, e o Google diz que dados intradiários e webhooks estão disponíveis para todos os tipos de dados relevantes. O acesso usa o `OAuth 2.0` do Google, e o Google classifica todos os escopos da Google Health API como restritos: até o seu app passar pela verificação do Google, ele fica limitado a 100 usuários, e apps que usam escopos restritos também precisam concluir uma avaliação de segurança anual feita por terceiros (CASA), que o Google diz levar de 2-3 semanas para apps tier-2 e de 4-6 semanas para apps tier-3, com taxas do avaliador de US$ 500 a US$ 4.500. O limite de requisições padrão é de 300 requisições por minuto por usuário. A contrapartida a conhecer: a [página da Google Health API do Google](https://developers.google.com/health/about) (lida em 14 de novembro de 2026) diz que o suporte à Fitbit Web API legada terminou em 30 de setembro de 2026 e dá 2 de novembro de 2026 como a data em que a API legada e os endpoints de OAuth da Fitbit são desligados, depois da qual as requisições falham com HTTP 410 Gone. O guia de migração do Fit do Google, atualizado em 10 de setembro de 2026, lista a Google Health API como o caminho recomendado para integrações com a Fitbit Web API, e o guia de migração da Health API do Google diz que os tokens existentes não podem ser transferidos, então planeje que todo usuário consinta de novo. A nossa página de [status da descontinuação da API da Fitbit](/fitbit-api-shutdown) separa o que está confirmado do que é só relatado. Confira os termos atuais na documentação.

## Garmin (Health API + Connect Developer Program)

A Garmin é uma boa escolha para casos de uso de resistência e atletismo. O programa dela se divide em uma Health API para métricas de bem-estar do dia todo — a página da Health API da Garmin lista passos, minutos de intensidade, sono, calorias, frequência cardíaca, estresse, Pulse Ox, Body Battery, composição corporal, respiração e pressão arterial — e uma Activity API para dados por atividade, como corrida, ciclismo e natação, com arquivos completos de atividade nos formatos .FIT, GPX e .TCX. O FAQ do programa da Garmin diz que todas as APIs do Developer Program usam `OAuth 2.0`, mas o acesso do lado do servidor aos dados de saúde de outros usuários exige se candidatar ao programa e ser aprovado — não é uma credencial autosserviço. Atenção: o programa empresarial da Garmin agora vem como Starter e Enterprise Access (visto pela primeira vez nas páginas dela em outubro de 2026). O Starter é só push, sem dados históricos e com capacidade de usuários limitada, e recursos como entrega por ping/pull, backfill e intervalo batimento a batimento aprimorado são marcados como disponíveis só com o Enterprise Access, em que a Garmin diz que os termos comerciais são ajustados. O FAQ da Garmin estima uma integração típica em 1 a 4 semanas depois que o seu pedido é aprovado, mas não diz quanto tempo leva a própria aprovação. Confirme que consegue ser aprovado antes de se comprometer com a Garmin; o [guia de integração da API da Garmin](/integrate/garmin-api) cobre o pedido de acesso e a configuração do OAuth 2.0. Se você só precisa dos seus próprios dados da Garmin, comece pela [Personal API oficial da Garmin para os seus próprios dados](/fix/garmin-api-personal-use); os dois clientes Python não oficiais são comparados em [garminconnect vs garth](/libraries/compare/garminconnect-vs-garth).

## API do Oura (v2)

O Oura é melhor para dados detalhados de sono, prontidão, HRV e recuperação a partir de uma API de anel bem documentada e de baixo atrito. A API v2 é o único ponto de integração suportado e devolve sono, prontidão e atividade diárias, frequência cardíaca, HRV, `SpO2`, treinos, sessões e estresse diário, tudo distribuído em oito escopos `OAuth 2.0` documentados que os usuários podem ligar e desligar um a um. Você registra uma aplicação OAuth em autosserviço; um app fica limitado a 10 usuários até você passar pela aprovação do Oura, depois da qual não há limite de usuários. Os limites de requisições valem por token e por aplicação, e o Oura documenta 5.000 requisições por período de 5 minutos. A contrapartida: os Personal Access Tokens foram descontinuados em dezembro de 2025, então agora é só `OAuth 2.0`, e os usuários precisam ter um anel Oura; a API devolve 403 quando a assinatura do Oura de um usuário expirou. Se um tutorial ainda manda você colar um token pessoal, a solução [tokens de acesso pessoal do Oura descontinuados](/fix/oura-personal-access-token-deprecated) cobre a passagem para o OAuth.

## API do WHOOP

O WHOOP é melhor para apps de coaching e de prontidão centrados em recuperação, esforço (strain) e HRV, construídos sobre o modelo fisiológico contínuo dele. A API expõe os ciclos de um membro, a recuperação (incluindo pontuação de recuperação, HRV e frequência cardíaca de repouso), o sono, os treinos com strain e as medidas corporais. Você mesmo precisa de uma assinatura do WHOOP para desenvolver um app; depois cria o app no Developer Dashboard para obter um Client ID e um secret e pede consentimento por escopo via `OAuth 2.0`, com access tokens de vida curta e suporte a webhooks. Todo app novo começa no nível Sandbox do WHOOP, que permite até 10 membros do WHOOP; para lançar de forma mais ampla, você pede o próximo nível pelo Developer Dashboard, e o WHOOP pede que você tenha testado com pelo menos um membro e preenchido o nome do app, os e-mails de contato e a URL da política de privacidade. Por padrão, o WHOOP permite 100 requisições por minuto e 10.000 por dia por cliente, com aumentos disponíveis mediante pedido. Atenção: os níveis acima do Sandbox (100, 1.000, 5.000 e depois membros ilimitados) são conquistados um de cada vez, por meio de uma revisão manual, e todo usuário que se conecta é um membro do WHOOP.

## Polar (Open AccessLink)

A Polar é melhor para acesso autosserviço e de baixo atrito a dados de treino, frequência cardíaca e GPS, além do Nightly Recharge, com tokens de vida longa que simplificam a gestão de tokens: o access token do próprio exemplo da Polar dura cerca de um ano. O Open AccessLink fica sobre os dados guardados no Polar Flow e devolve exercícios (com duração, distância, zonas de frequência cardíaca e amostras como frequência cardíaca, velocidade, cadência e altitude, exportáveis em `TCX` ou `GPX`), atividade diária, Nightly Recharge (baseado na HRV e na frequência cardíaca noturna, com carga do SNA e frequência respiratória), sono e frequência cardíaca contínua, e pode enviar webhooks quando os dados de um usuário estão prontos. Você registra um cliente em autosserviço no portal de administração do AccessLink usando as credenciais do Polar Flow; note um detalhe do fluxo — depois da autorização `OAuth 2.0`, você precisa registrar o usuário explicitamente com um POST no endpoint de usuários para vincular a conta dele ao seu app. A contrapartida a conhecer: a API expõe só dados recentes — exercícios enviados ao Flow nos últimos 30 dias, e só os enviados depois que o usuário se registrou no seu cliente, e sono e Nightly Recharge dos últimos 28 dias —, então você precisa consultar ou exportar (JSON, `FIT`, `TCX` ou `GPX`) com regularidade para manter o histórico completo. O que fica do seu lado da conta está em [preço do Polar AccessLink](/pricing/polar-api-pricing).

## Qual escolher?

Combine a API com o seu caso de uso em vez de caçar um único vencedor:

- **Se você precisa de GPS e multiesporte a sério e de uma longa lista de métricas de saúde do dia todo** (Body Battery, Pulse Ox, estresse, respiração) → escolha a Garmin, mas confirme antes que consegue passar pela aprovação da Garmin no nível de acesso de que precisa, já que o Starter Access é só push e ping/pull e backfill são só do Enterprise.
- **Se você precisa de dados profundos de sono, prontidão e recuperação com baixo atrito de entrada** → escolha o Oura, para o anel, ou o WHOOP, para um modelo contínuo de esforço e recuperação. Lembre que os dois limitam você a 10 usuários ou membros até passar pela aprovação, e que todo usuário do WHOOP é um membro do WHOOP.
- **Se você quer o maior alcance de dispositivos no grande público e dados ricos de frequência cardíaca e sono intradiários** → escolha a Fitbit pela Google Health API, e reserve tempo e orçamento para a verificação do app e a avaliação de segurança do Google e para o novo consentimento de todo usuário existente.
- **Se você quer lançar rápido com o menor atrito de aprovação** → escolha a Polar, cujo registro de cliente autosserviço e os access tokens de um ano do exemplo da Polar fazem dela a opção mais autosserviço daqui, desde que você consiga conviver com apenas os dados recentes disponíveis e os sincronize com regularidade.
- **Se você está conectando uma força de trabalho inteira para um programa de bem-estar de uma empresa** → comece pela mistura de dispositivos e pelos portões de acesso, que [APIs de dados de wearables para programas de bem-estar corporativo](/fitness-apis/corporate-wellness-wearable-apis) mapeia rota por rota.
- **Se você quer muitos wearables e sensores atrás de uma única integração em vez de cinco** → você quer um agregador, não uma destas APIs; as [melhores APIs agregadoras de dados de saúde de wearables](/fitness-apis/health-data-aggregator-apis) são comparadas por caso de uso na página delas.

## Atenção às letras miúdas

Modelos de preço, limites de requisições, tetos de usuários e datas de migração mudam com frequência nesta categoria. Tudo o que está acima foi conferido na documentação de cada fornecedor em 14 de novembro de 2026, e você deve confirmar os números e os termos comerciais atuais na documentação de desenvolvedores de cada fornecedor antes de construir, principalmente para qualquer coisa que rode em escala.
